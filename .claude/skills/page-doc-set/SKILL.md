Generate (or refresh) the **full page-doc set** for one FE page so the owner and you share one
accurate, code-traced picture of the page — its BE endpoints, its data flow, and its loading
behaviour — with nothing in `docs/system/` left stale. The **Backend View** (`<page>_be.md`) is
the anchor and is built in this session with full rigour (Steps 0–7); the **remaining files of the
6-file folder** are generated by **spawning one subagent per file** (the "Widen" step), each
following [`docs/system/08_pages/PAGE_FOLDER_GUIDE.md`](../../../docs/system/08_pages/PAGE_FOLDER_GUIDE.md).

The argument is: $ARGUMENTS — a page identifier: a folder/file name under
`docs/system/08_pages/` (e.g. `customer_menu`, `staff_kds`, `admin_overview`) or a route
(e.g. `/menu`, `/pos`).

**The canonical output to copy the shape from:** the gold-standard folder
`docs/system/08_pages/customer/customer_menu/` — its `customer_menu_be.md` (BE anchor) plus
`customer_menu.md`, `customer_menu_crosscomponent_dataflow.md`,
`customer_menu_crosspage_dataflow.md`, `customer_menu_loading.md`. The recipe for each is
`PAGE_FOLDER_GUIDE.md` §1–§7.

**The 6-file set this skill produces** (per `PAGE_FOLDER_GUIDE.md` §1 — build only the rows that
apply to this page):

| # | File | When it applies | Built by |
|---|---|---|---|
| 1 | `<page>.md` | Always | Widen agent (guide §2) |
| 2 | `<page>_be.md` | Page calls BE | **This session, Steps 0–7 (anchor)** |
| 3 | `<page>_crosscomponent_dataflow.md` | ≥3 interacting widgets + shared store | Widen agent (guide §4) |
| 4 | `<page>_crosspage_dataflow.md` | Page hands data off (writes outlive it) | Widen agent (guide §5) |
| 5 | `<page>_loading.md` | Page fetches async data | Widen agent (guide §6) |
| 6 | `SCENARIO_<PAGE>.md` | Always — a narrative built around THIS page's own flows | Widen agent (guide §7) |

**Golden rule — code is the source of truth.** Every endpoint row, file:line, cache key, auth
note, and field name is a claim about the running Go code on the current branch. **Read the
source, do not recall it.** If a fact cannot be confirmed from a file, write `❓ UNVERIFIED` —
a short honest doc beats a complete wrong one. When source and any `docs/system` file disagree,
**the code wins**: fix the doc and log the drift (Step 6).

**Three jobs, not one.** This skill (1) WRITES the page's `_be.md` anchor with full BE rigour;
(2) GENERATES every remaining file of the 6-file set by spawning one subagent per file (the Widen
step); and (3) UPDATES `docs/system` so the new facts are reflected everywhere. Do not skip job 2
("generate all remaining files") or job 3 ("ensure update all information and data in docs/system").

**Finish in one session — fan out with subagents.** A page calls several endpoints, needs several
sibling docs, and touches several `docs/system` files; doing them one at a time blows the session
budget. So **spawn as many subagents as you need to finish in a single session** — the rule of
thumb is **one agent per independent file/unit of work**, run in parallel, then assembled by this
session. You (the orchestrator) stay the single writer of the `_be.md` anchor and of the shared
aggregation files (TRACKER, PAGES_INDEX, README, LOGIC_INDEX); the agents do the read-heavy
tracing, write the sibling docs, and make per-domain edits, then **report back** so you stitch the
results together. Details inline at Step 2 (endpoint trace), Step 5b (Widen — sibling files), and
Step 6 (doc sync), with the full pattern in **Parallel Execution** below.

## Parallel Execution — Spawn Subagents (one per file)

The three expensive loops in this skill — tracing N endpoints through Go (Step 2), generating the
N sibling docs of the 6-file set (Step 5b), and syncing M handbook files (Step 6) — are
embarrassingly parallel. Fan them out so the whole page folder closes in one session.

**The pattern:**
1. **List the units of work** first — the endpoints to trace, then the independent docs files to
   sync. Each unit = one agent.
2. **Spawn one agent per unit, in parallel** (multiple `Agent` calls in a single response).
   Default model **Sonnet 4.6** (`model: "sonnet"`) — tracing/editing is normal work per
   `docs/MODEL_SELECTION.md`; keep this Opus session as the orchestrator.
3. **Give each agent a self-contained brief**: the exact file(s) to read, the branch, the one
   thing to return, and the rule *"read the source, do not recall it; cite `file:line` for every
   claim; if you cannot pin a fact to a line, return `❓ UNVERIFIED`."* An agent starts cold — it
   has none of your context, so spell out paths.
4. **Request completion and collect** every agent's report before you write. The agent's final
   message is the tool result — relay only what you verified into the doc.
5. **You remain the only writer** of the final `_be.md` and of the shared aggregation files
   (`BE_DOC_TRACKER.md`, `PAGES_INDEX.md`, `README.md`, `LOGIC_INDEX.md`). Never let two agents
   edit the same file — that is a write conflict. Per-domain files (one agent each) are safe;
   shared roll-up files are serial and yours.

**Read-only vs. writing agents:** Step-2 trace agents are read-only — prefer `Explore` or
`general-purpose`. Step-5b sibling-doc agents and Step-6 sync agents WRITE one file each — use
`general-purpose` (it can Read/Write/Edit). Use `isolation: "worktree"` only if the owner wants
the doc edits sandboxed; default is in-place.

**Cross-links are by predictable filename, so siblings can be generated in parallel** even before
each other exists: an agent writing `<page>_loading.md` links to `<page>.md` and `<page>_be.md` by
their known paths — it does not need them on disk first. So the Widen agents (Step 5b) all fan out
at once; you do not serialize them.

**When NOT to fan out:** don't spawn one agent to do one trivial thing. Fan out when there are
**3+ endpoints** to trace, **2+ sibling files** to generate, or **3+ independent files to sync**.
The goal is finishing the page folder in one session, not maximizing agent count.

## Step 0 — Read the tracker, then resolve the page and its neighbours

0. **Read the tracker** `docs/system/08_pages/BE_DOC_TRACKER.md`. Find this page's row — note prior
   status/concerns (a ✅ row means this is a refresh). If the page has no row, add one. If the row
   is ❌ (PLANNED) or N/A (no BE calls), respect it: STOP and confirm with the owner before writing.
1. Find the page in [`docs/system/08_pages/PAGES_INDEX.md`](../../../docs/system/08_pages/PAGES_INDEX.md) →
   get its route and its FE doc file (`08_pages/<page>.md`). If the page is not in the index,
   STOP and ask the owner which route/page they mean.
2. Read the **FE sibling doc** `08_pages/<page>.md` in full — its Zones table tells you which
   components call which endpoints, and its Object Model / Flags sections must stay consistent
   with what you write. The `_be.md` is the BE twin of this file and links back to it.
3. Locate the page's real FE code: `fe/src/app/.../<page>/page.tsx` and the components/hooks it
   renders. You need these only to enumerate **which endpoints the page actually calls** (the BE
   tracing happens in Go).

If the page has no `page.tsx` yet (🔮 PLANNED) → STOP and tell the owner the BE doc would be
speculative; offer to base it on the planned spec, clearly labelled `(planned, not yet coded)`.

## Step 1 — Enumerate the endpoints this page calls

From the FE sibling doc + the page's hooks/mutations/`lib/api-client.ts` calls, list **every**
endpoint the page hits (reads and writes). For each, capture the method + path (e.g.
`GET /products`, `POST /orders`, `POST /orders/:id/items`). This list becomes the rows of the
**Endpoints Used by This Page** table. Do not add endpoints the page never calls.

## Step 2 — Trace each endpoint through the Go source (source of truth)

> **Fan out here (one agent per endpoint).** With 3+ endpoints, spawn **one trace agent per
> endpoint** in parallel (read-only — `Explore` / `general-purpose`, model `sonnet`). Brief each
> with: the method+path, the branch, "trace route→handler→service→repo/sqlc→Redis and return the
> full chain with a `file:line` for every hop; `❓ UNVERIFIED` for anything you can't pin to a
> line." Collect all reports before writing Step 4. You keep the file:line citations verbatim —
> do not paraphrase a line number an agent gives you; if it looks off, re-open the file yourself.

For every endpoint, open the real Go files and record the chain with `file:line`:

1. **Route registration + middleware** → `be/cmd/server/main.go` (route group, `authMW`,
   role gates like `AtLeast("manager")`). Record auth model per endpoint.
2. **Handler** → `be/internal/handler/<domain>_handler.go` — binding, query params actually
   read (note any the FE sends that the handler ignores → a Flag), the serializer used.
3. **Service** → `be/internal/service/<domain>_service.go` — business logic, cache get/set,
   snapshotting, combo expansion, total recalc, etc.
4. **Repository / sqlc query** → the exact query name (`ListProductsAvailable`, tx inserts…).
5. **Redis cache** → key name + TTL + invalidation trigger, if any.

Keep a `file:line` for every non-trivial claim. Anything you cannot pin to a line → `❓ UNVERIFIED`.

## Step 3 — Cross-check every claim against docs/system (required)

Before writing, reconcile each part of the doc against the handbook file that owns that fact.
For each row below: if the doc and the code **agree**, cite the doc as the deep-dive link; if they
**disagree**, the code wins — note the mismatch for Step 6 sync.

| Part of the `_be.md` | Cross-check against (owner of that fact) |
|---|---|
| Endpoints table / route map | `02_spec/API_SPEC.md` · `03_be/BE_CODE_SUMMARY.md` (route map) |
| Auth model per endpoint (public / authMW / role) | `02_spec/BUSINESS_RULES.md` (RBAC) · `main.go` middleware |
| Request / response **key fields** | `02_spec/API_SPEC.md` (Key Request/Response Fields) |
| Field / column names | `02_spec/DB_SCHEMA.md` (single source of field names) |
| Caching keys, TTL, invalidation | `03_be/REDIS_CACHE.md` · `10_caching/CACHE_FLOW_E2E.md` |
| Error behaviour / codes | `02_spec/ERROR_SPEC.md` |
| Realtime (only if page uses SSE/WS) | `03_be/REALTIME_SSE.md` · relevant `01_flow/*` |
| Order write pipeline / snapshots / combo expansion | `02_spec/OBJECT_MODEL_ORDER.md` · `07_business_logic/LOGIC_BE.md` |
| Business rules (one-active-order, cancel, payment) | `02_spec/BUSINESS_RULES.md` · `07_business_logic/LOGIC_BE.md` |
| Layer rules (handler→service→repo→sqlc) | `03_be/BE_TECH_SUMMARY.md` |
| FE-side consistency (flags, object shapes) | the FE sibling `08_pages/<page>.md` |

Skip a row only if the page genuinely has nothing in that category (e.g. no realtime).

## Step 4 — Write the page `_be.md`

Path: `docs/system/08_pages/<category>/<page>/<page>_be.md` — same per-page folder as the FE doc
(e.g. FE doc `08_pages/customer/customer_menu/customer_menu.md` → BE doc
`08_pages/customer/customer_menu/customer_menu_be.md`; FE doc `08_pages/staff/staff_kds/staff_kds.md`
→ `08_pages/staff/staff_kds/staff_kds_be.md`).

Mirror the section order of `customer_menu_be.md` exactly (omit a section only if it doesn't apply):

1. **H1 + TL;DR blockquote** — one-line purpose; a `Sources:` line listing the exact Go files
   traced; the branch name; and cross-links to the FE sibling doc + any object-model doc.
2. **`## Endpoints Used by This Page`** — the table: `# | Endpoint | Auth | Handler | Service |
   Repo / Query | Redis cache`. Follow with the route-registration `file:line`.
3. **`## Auth Model on This Page`** — public vs authMW vs role-gated, guest-JWT behaviour,
   `created_by` rules.
4. **`## Per-Endpoint Detail`** — one `### N · METHOD /path` block per endpoint, each citing
   `file:line` for handler/service/repo and describing cache + special logic.
5. **`## Caching & Invalidation`** — keys, TTL, write-triggered invalidation, failure behaviour.
6. **`## Error Behaviour`** — bind failures, service-error mapping, FE-visible states.
7. **`## Flags`** — numbered table of mismatches/gotchas (params ignored, response-only fields,
   missing middleware…). Cross-reference the FE sibling's flags where they match.

Use `---` separators between sections, matching the model file.

## Step 5 — Verification pass (do not skip)

Re-open each handler/service once more and confirm every cell. Any claim you could not pin to a
line → downgrade to `❓ UNVERIFIED`. Confirm the Endpoints table lists only endpoints the page
actually calls, and that each `file:line` still resolves.

## Step 5b — Widen: generate the rest of the page folder (job 2 — spawn one agent per file)

The `_be.md` anchor is done. Now produce the **remaining files of the 6-file set** so the page
folder matches the gold standard `customer_menu/`. **You do not write these yourself — you spawn
one `general-purpose` subagent per file, in parallel** (`model: "sonnet"`), and collect their
reports. The single recipe every agent follows is
[`docs/system/08_pages/PAGE_FOLDER_GUIDE.md`](../../../docs/system/08_pages/PAGE_FOLDER_GUIDE.md).

**1. Decide which files to build.** From the 6-file table in the intro + `PAGE_FOLDER_GUIDE.md` §1
"When it applies", select the rows that apply to THIS page. Then check the folder on disk:
- File **missing** + applies → spawn an agent to **create** it.
- File **exists** → leave it, unless the owner asked for a refresh or your Step-2 trace contradicted
  it (then refresh, citing the corrected fact). Never blank-overwrite a current file.
- File **does not apply** (e.g. a static page that fetches nothing → no `_loading.md`) → skip and
  note why in the report.
- **`SCENARIO_<PAGE>.md` is page-specific and always built** (not the shared `SCENARIO_LUNCH_RUSH`).
  Name it after the page's primary flow, e.g. `SCENARIO_MENU_ORDER.md` for `customer_menu`,
  `SCENARIO_KDS_COOK.md` for `staff_kds`. Build the narrative around **this page's own** traced
  endpoints (from the `_be.md` anchor you just wrote) and its own cross-component / cross-page
  flows — one concrete run through this page, end to end. If a shared scenario already covers the
  page well, the page scenario should **zoom in on this page's beat** and link out to the shared
  one rather than duplicate it.

**2. Spawn one agent per file, all in one response.** Each brief MUST be self-contained — the agent
starts cold:
- **The exact output path**, e.g. `docs/system/08_pages/customer/customer_menu/customer_menu_loading.md`.
- **Its recipe:** "Follow `PAGE_FOLDER_GUIDE.md` §<N> (the section for this file type) for the
  section skeleton and rules." Name the section number explicitly:
  §2 = `<page>.md` · §4 = `_crosscomponent_dataflow.md` · §5 = `_crosspage_dataflow.md` ·
  §6 = `_loading.md` · §7 = `SCENARIO_<PAGE>.md`. For the scenario, also hand the agent the
  endpoint list + flows from the `_be.md` you just wrote, so its narrative is grounded in this
  page's real BE calls.
- **Its model file** to copy the shape from, e.g.
  `customer/customer_menu/customer_menu_loading.md`.
- **The page's real source** to trace: `fe/src/app/.../<page>/page.tsx`, its components, hooks,
  store (`fe/src/store/*`), payload builders (`fe/src/lib/*`), SSE hooks
  (`fe/src/hooks/useOrder*SSE.ts`), `fe/src/lib/storage-keys.ts`, types (`fe/src/types/*`) — list
  the ones relevant to that file type per the guide.
- **The sibling filenames** for cross-links (they are predictable — give them so links resolve even
  though siblings may still be generating).
- **The non-negotiables:** "Code wins — trace from source on the current branch, do not recall;
  cite `file:line` for every claim; `❓ UNVERIFIED` for anything you can't pin to a line; TL;DR
  header on the file; one model, one home — link to a fact's owner instead of restating it; make
  ONLY this one file."
- **What to return:** the path written, a list of any `❓ UNVERIFIED` cells, and any code-vs-doc
  drift it noticed (you fold that drift into Step 6).

**3. Hard rule — one agent, one file. Never two agents on the same file.** The sibling docs are
disjoint, so this is naturally safe. The shared roll-up files (`PAGES_INDEX`, `README`, `TRACKER`,
`LOGIC_INDEX`) are **off-limits to these agents** — you alone touch them in Step 6.

**4. Collect every report** before moving on. Carry each agent's drift findings into Step 6 and its
`❓ UNVERIFIED` count into the Step 7 report. If an agent reports it could not trace a file from
source (page not coded / 🔮 PLANNED), do not let it guess — have it write the file labelled
`(planned, not yet coded)` or skip and flag to the owner.

## Step 6 — Sync docs/system (job 3 — required)

This is the "ensure update all information and data in docs/system" requirement. Propagate every
fact that the source proved but the handbook had wrong or missing. Make **minimal, surgical**
edits — fix only what the trace contradicted; do not rewrite unrelated prose.

> **Fan out here too (one agent per independent domain file).** Each disagreement in step 1 below
> usually lives in a *different* file (`DB_SCHEMA.md`, `API_SPEC.md`, `REDIS_CACHE.md`,
> `ERROR_SPEC.md`…). Spawn **one sync agent per such file** in parallel (`general-purpose`, model
> `sonnet`), each with: the exact file, the stale fact, the corrected fact + its `file:line`
> proof, and "make a minimal surgical edit, do not restructure or rewrite unrelated prose; if the
> fix changes business meaning rather than a stale fact, STOP and report instead of editing."
> **Keep the shared roll-up files serial and yours** — you alone edit `LOGIC_INDEX.md`,
> `PAGES_INDEX.md`, `README.md`, and `BE_DOC_TRACKER.md` (sub-steps 2–5) so the Decision Log and
> indexes stay conflict-free. Two agents must never target the same file.

1. **For each disagreement found in Step 3** → fix the owning `docs/system` file (e.g. correct a
   field name in `DB_SCHEMA.md`, an endpoint in `API_SPEC.md`, a cache key in `REDIS_CACHE.md`).
2. **Log the drift** in `07_business_logic/LOGIC_INDEX.md` Decision Log (the handbook rule:
   code wins → fix the summary AND log the drift). One line: date · what was stale · corrected to.
3. **`08_pages/PAGES_INDEX.md`** → ensure the page row links **every file produced this run**, not
   just the `_be.md` (e.g. `[customer_menu.md](…/customer_menu.md) · [BE](…/customer_menu_be.md)`
   plus links to the `_crosscomponent_dataflow`, `_crosspage_dataflow`, and `_loading` siblings that
   were created). Additive links only.
4. **`docs/system/README.md`** → ensure the new docs are discoverable. If a "Per-Page" list/note
   does not exist, add the page-folder reference in the Data Model Map row
   "Per page → which endpoints it calls" (it already points at `08_pages/`); keep the edit small
   and additive. **Do not restructure README tables** — additive links only.
5. **`08_pages/BE_DOC_TRACKER.md`** → update this page's row: set Status (✅ if every cell traced
   + docs synced; ⚠️ if any `❓ UNVERIFIED` / open drift / code bug), fill `Last Run` with today's
   date, and write a one-line concern/note.

   **Every finding lands here — no finding may exist only in a sub-file.** The TRACKER is the single
   index of what each run discovered, so before you close the run, sweep ALL findings from this run
   into it. A "finding" is anything the trace surfaced that a future reader needs to know:
   - a **doc drift** fixed in Step 6 (what was stale → corrected to);
   - a **code bug** written to `<PAGE>_BUGS.md` in Step 6b (severity + 1-line + the bug-file link);
   - a **`❓ UNVERIFIED` cell** (count + which file/cell) carried up from the anchor or any Widen agent;
   - a **flag / gotcha** from the `_be.md` Flags section worth surfacing (ignored param, dead output,
     non-transactional write, auth quirk, asymmetric cache invalidation…);
   - a **cross-page fact** — shared endpoint / cache key / auth gate / bug root that touches more than
     one page's BE doc.

   Put each finding in the right place and never both summarise-and-drop:
   - **The page row's Concerns/Notes cell** gets the page-local findings (drift, bugs, unverified,
     flags) condensed to one line each, mirroring the existing rows (C4/A3/A8 are the model density).
   - **The Cross-Page Concerns section** gets a bullet for every finding that touches >1 page — name
     the pages, the shared file:line, whether it is fixed/open, and where it is logged. If this run
     *confirms or extends* an existing Cross-Page bullet, append to that bullet (as the A9→A8 entry
     does) rather than adding a duplicate.

   If a finding has no home yet (a brand-new shared concern, a flag class not seen before), create it
   here — the TRACKER is allowed to grow. The only thing not allowed is a finding that the run proved
   but the TRACKER does not mention.

> ⚠️ Never modify a table in any `command.md` as part of this skill. README/PAGES_INDEX edits are
> additive links only. If a sync edit would change business meaning (not just a stale fact), STOP
> and flag it to the owner before editing — `🔴 STOP` / `⚠️ FLAG`.

## Step 6b — Capture code bugs in `<PAGE>_BUGS.md` (when the trace finds real bugs)

A trace surfaces two different kinds of problem, and they are handled differently:

- **Doc drift** — a `docs/system` file is stale, the code is right → fixed in Step 6 (correct the
  doc + log in the Decision Log). The doc skill *can* resolve these.
- **Code bug** — the running FE and BE code disagree with each other (or with clear intent): an
  event type the publisher emits but no consumer matches, a returned value never wired to UI, an
  ownership check present on one path and missing on its twin, a dead constant. **A doc edit cannot
  fix these — only an app-code change can.** The doc skill must NOT touch app code; instead it
  records the bug so the owner can act.

**When this step fires:** the run found ≥1 genuine code bug (not just a stale doc). If the trace
found none, skip this step and say so in the report.

**What to do — you (the orchestrator) write one file, never an agent:**

1. **Write `docs/system/08_pages/<category>/<page>/<PAGE>_BUGS.md`** (e.g. `TRACKING_BUGS.md`,
   `KDS_BUGS.md`). Model the shape on
   [`customer/customer_tracking/TRACKING_BUGS.md`](../../../docs/system/08_pages/customer/customer_tracking/TRACKING_BUGS.md):
   - **TL;DR blockquote** — count of bugs, the branch traced, the rule "these are *code* bugs not
     stale docs; the doc skill does not fix app code", and links to the Decision Log entry + `_be.md`.
   - **Severity-at-a-glance table** — `# | Bug | Severity (🔴 High/🟠 Med/🟡 Low) | Surface affected
     (note if cross-cutting) | Fix side (FE/BE)`.
   - **One `## Bug N` section each** — Symptom (what the user sees) → Root cause (with `file:line`
     for the publisher AND the consumer) → Suggested fix (smallest safe change; mark which side).
   - **A "Next step" footer** — these bugs are NOT yet on `docs/tasks/MASTER_TASK.md`; per CLAUDE.md
     a fix must be registered + ALIGNed before any code change. Recommend the highest-impact one.
   - Every claim cited to source; `❓ UNVERIFIED` for anything not pinned to a line. Relative links
     back to `fe/`/`be/` look like `../../../../../fe/src/...`.
2. **Cross-link both ways:** add a one-line pointer from the `_be.md` Flags section into
   `<PAGE>_BUGS.md` (so a reader of the BE view finds the bugs), and link the Decision Log entry +
   `_be.md` from inside the bug file.
3. **Log once in the Decision Log** (Step 6.2) as a `⚠️ DRIFT` row that names the bug file — do not
   duplicate the full bug detail there; the bug file is the home (Rule #9).
4. **Note it on the TRACKER row** (Step 6.5): mark the page `⚠️` and summarise the open bugs in the
   concern note; add a **Cross-Page Concern** bullet if a bug touches a hook/route/endpoint shared
   by more than one page (e.g. a shared SSE hook).
5. **Surface in Step 7** and to the owner: end the turn by offering to register the top bug in
   `MASTER_TASK.md` — never start the fix unprompted (that is a separate, ALIGNed task).

> The bug file is the durable home for "things the trace proved are broken in code". Keep it
> code-bug-only — stale-doc fixes belong in Step 6, not here.
